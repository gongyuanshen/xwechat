# 第一轮补齐：恢复到当前资料库

**目标：** 用户选择备份后，经过临时校验把缺失资料写回本机，直接在资料夹和事项页面使用。用户已明确选择“补回缺失资料，冲突时保留本机版本”。

**根因：** 上一实现把“隔离目录恢复验收”当成最终产品功能，未接入活库；资料账号又依赖聊天账号，缺少聊天库时已恢复记录仍不可见。本计划取代旧说明中“仅隔离恢复”的产品边界。

## 已确定的行为

- 沿用现有备份格式、完整性校验及临时恢复流程。临时目录仅用于校验，不再作为用户的恢复结果。
- 已存在的同账号记录保持不变；缺失记录按关系顺序插入。不使用共享库整体替换或 UPSERT 覆盖。
- 不同 ID 的同序号专题版本保留本机版本；依赖冲突导致不能纳入的记录明确计入 skipped 并列原因。
- 附件补缺包括仅历史版本引用、已存在资料但实体缺失的情况；现有实体摘要冲突明确拒绝，不覆盖。其他账号 ID 碰撞整次拒绝。
- 仅为本次新恢复的事项导入其未投递提醒，以现有 unique_key 去重并使用新事件序号；重复恢复不重新投递旧提醒。本机已有事项和提醒状态不变。
- 实际恢复在现有账号生命周期互斥及 SQLite 事务下提交；附件先完成并核对，再提交引用它们的记录。失败回滚记录、清理本次新发布文件，不触碰旧文件。
- 资料页使用独立应用资料账号列表，包含真实聊天账号及 AIStore 中的资料账号。不会伪造聊天目录或把资料账号加入聊天列表。
- 已恢复的笔记、报告、专题、事项、保存搜索及附件可独立查看/编辑；跳转原消息或重查搜索仍需原聊天数据库。

## 接口

- `POST /api/data-backup/restore`：multipart `file`，执行临时校验和活库补缺。返回 `status=restored`、`account`、归档 `counts`、实际 `added` / `kept` 分类数量、`skipped` 原因列表、附件字节数、内容摘要及正式 `data_path`。
- `GET /api/library/accounts`：`accounts` 为应用资料可用账号，`chat_accounts` 为真实聊天账号；AIStore 资料账号读取及新接口请求失败明确报错。微信账号枚举复用现有查询，本轮不重构其既有错误处理。
- 现有资料/事项接口读取应用资料账号；创建原文资料、重新确认改期等操作继续使用真实来源校验。
